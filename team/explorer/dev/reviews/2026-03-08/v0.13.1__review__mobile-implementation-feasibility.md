## 1. Implementation Feasibility: Can We Run `tauri ios init` / `tauri android init` Today?

**Short answer: Yes, with minor adjustments.**

The codebase is already structured for mobile compatibility. Key evidence:

- **`lib.rs` already has the mobile entry point annotation:**
  ```rust
  #[cfg_attr(mobile, tauri::mobile_entry_point)]
  pub fn run() {
  ```
  This is the standard Tauri 2.0 pattern for dual desktop/mobile builds. The code compiles for mobile targets without modification.

- **`Cargo.toml` has the correct crate types:**
  ```toml
  crate-type = ["lib", "cdylib", "staticlib"]
  ```
  `staticlib` is required for iOS (static linking into the Swift binary), `cdylib` for Android (JNI shared library). Both are already present.

- **`main.rs` is desktop-only, which is correct.** On mobile, Tauri uses the `mobile_entry_point` macro from `lib.rs` instead.

**Changes needed before `tauri ios init` / `tauri android init`:**

| Change | Effort | Detail |
|--------|--------|--------|
| `tauri.conf.json` — add `bundle.iOS` and `bundle.android` sections | Trivial | Tauri init commands scaffold these automatically |
| Icons — add required mobile icon sizes | 30 min | iOS needs 1024x1024 AppIcon, Android needs mdpi through xxxhdpi. Use `cargo tauri icon` to generate from a source image |
| CSP update | 5 min | Current CSP in `tauri.conf.json` already permits `connect-src https://*.sgraph.ai; frame-src https://*.sgraph.ai` — this will carry over to mobile |
| Xcode + Android SDK prerequisites | Variable | Developer machine needs Xcode 15+ and/or Android Studio + SDK 24+. CI machines need these too |

**No Cargo.toml changes required.** The existing dependencies (`tauri`, `tauri-plugin-opener`, `serde`, `serde_json`, `url`) all compile for iOS and Android targets.

## 2. Remote Webviews on Mobile: The Critical Question

This is the **highest-risk area** of the mobile port. The desktop app's core architecture is loading remote `*.sgraph.ai` URLs in native webviews.

### How It Works on Desktop

`webviews.rs` creates child webviews using `WebviewBuilder::new(&label, WebviewUrl::External(parsed_url))` and positions them alongside the sidebar. This is a **multi-webview architecture** — the main window has a local webview (sidebar/status bar) plus separate native webviews for each remote site.

### iOS (WKWebView)

- **Remote URL loading works.** WKWebView loads remote URLs by default. Apple does not restrict loading remote content in WKWebView for non-App-Store apps (TestFlight, enterprise distribution).
- **App Store review risk:** Apple reviewers may flag an app that is "primarily a web wrapper." Apple's guideline 4.2 ("Minimum Functionality") rejects apps that are "simply a web site bundled as an app." Mitigation: the app must demonstrate native value beyond the web content (Keychain integration, biometric auth, offline capabilities).
- **Multi-webview support on iOS:** Tauri 2.0 supports multi-webview on iOS, but the `add_child` API with manual positioning (`LogicalPosition`, `LogicalSize`) behaves differently. On iOS, Tauri typically uses a single webview or a navigation-based model. The current `activate_site` pattern of creating child webviews at pixel positions will need testing — it may work but could have layout/scrolling edge cases.

### Android (Android WebView)

- **Remote URL loading works.** Android WebView loads remote URLs. No Play Store restriction on remote content loading.
- **Multi-webview:** Same concern as iOS. The `add_child` positioning model may behave differently. Android's WebView doesn't have the same compositing model as macOS WebKit.
- **Mixed content:** Android WebView may block mixed HTTP/HTTPS content by default. Not an issue since all `*.sgraph.ai` URLs are HTTPS.

### Verdict

Remote webview loading is feasible on both platforms. The multi-webview child positioning pattern (`window.add_child` with `LogicalPosition`/`LogicalSize`) is the main uncertainty and should be the first thing tested in a proof-of-concept.

## 3. Current Code Audit for Mobile Readiness

### Rust Code — `src-tauri/src/commands/webviews.rs`

**Desktop-specific patterns that need mobile adaptation:**

1. **Hardcoded layout constants:**
   ```rust
   const SIDEBAR_WIDTH: f64 = 60.0;
   const STATUS_BAR_HEIGHT: f64 = 28.0;
   ```
   On mobile, sidebar width should be 0 (no sidebar — bottom tabs instead), and status bar height needs adjustment for iOS safe areas (notch, dynamic island) and Android system bars. These constants must become platform-conditional or configurable.

2. **`window.inner_size()` / `window.scale_factor()`:** These APIs exist on mobile Tauri, but the values differ. iOS devices have scale factors of 2.0 or 3.0. The math should still work, but needs testing.

3. **`wv.show()` / `wv.hide()`:** Webview show/hide is supported on mobile but less common. On mobile, the convention is to use a single visible webview with navigation, not multiple hidden/shown webviews. Performance concern: multiple hidden webviews consume memory. On a 4GB iPhone, keeping 4 remote webviews loaded may cause memory pressure.

4. **`toggle_devtools`:** DevTools is desktop-only. `wv.is_devtools_open()` / `wv.open_devtools()` will likely be no-ops or panic on mobile. This command should be gated:
   ```rust
   #[cfg(not(mobile))]
   ```
   or return a no-op on mobile.

5. **`disable_drag_drop_handler()`:** Not meaningful on mobile (no drag-and-drop), but should compile without issue as a no-op.

### JS Code — Desktop-Only Patterns

1. **`app-shell.js` — Keyboard shortcut `Cmd+Option+I`:**
   ```js
   document.addEventListener('keydown', (e) => {
       if (e.metaKey && e.altKey && e.key === 'i') { ... }
   })
   ```
   Harmless on mobile (no physical keyboard in normal use), but dead code. Low priority.

2. **`sidebar.js` — Vertical sidebar navigation:**
   The entire sidebar component renders as a vertical icon bar. On mobile, this should be a bottom tab bar. The component itself is simple enough (40 lines of template + event handling) that creating a mobile variant (`sg-bottom-nav`) or making `sg-sidebar` responsive via CSS is straightforward.

3. **`status-bar.js`:** The footer status bar showing URL and status. On mobile, this wastes valuable screen space. Should be hidden or collapsed on mobile.

4. **`site-manager.js`:** Calls `window.__TAURI__.core.invoke('activate_site', ...)`. This is platform-agnostic and will work on mobile without changes.

### CSS — Not Reviewed in Detail

The CSS files (`theme.css`, `reset.css`, component CSS) were not part of the read scope, but the architecture (separate CSS files per component, CSS custom properties) supports responsive adaptation via media queries.

## 4. Tauri Plugins Needed for Mobile Features

| Feature | Plugin | Status | Notes |
|---------|--------|--------|-------|
| **Biometric auth** | `tauri-plugin-biometric` | Stable (v2) | Face ID, Touch ID (iOS), fingerprint (Android). Requires `NSFaceIDUsageDescription` in Info.plist |
| **Camera** | `tauri-plugin-barcode-scanner` | Stable (v2) | Gives camera access but for barcode scanning. For general photo capture, use web APIs (`getUserMedia`) or a community plugin |
| **Camera (photo capture)** | Web API `navigator.mediaDevices` | Built into WebView | Works in WKWebView and Android WebView. Requires `NSCameraUsageDescription` (iOS) |
| **Share sheet** | `tauri-plugin-sharesheet` (community) | Experimental | No official Tauri plugin. Requires custom Swift (iOS) / Kotlin (Android) plugin. Medium effort |
| **Push notifications** | `tauri-plugin-notification` | Stable (v2) | Local notifications. For remote push (APNs/FCM), requires custom integration or `tauri-plugin-push-notifications` (community, less mature) |
| **Offline queue** | No plugin needed | N/A | Implement in Rust using `serde` for serialization + local file storage. The app already has `serde` and `serde_json` |
| **File picker** | `tauri-plugin-dialog` | Stable (v2) | Replaces drag-and-drop on mobile. File picker dialogs on both platforms |
| **Haptic feedback** | `tauri-plugin-haptics` | Stable (v2) | Optional but improves mobile UX |

**Key gap:** Share sheet integration is the hardest mobile feature. There is no mature official plugin. It requires writing a Share Extension (iOS) or implementing `Intent`/`ShareCompat` (Android) — this is native platform code, not just a Tauri plugin.

## 5. CI/CD Extension for Mobile Builds

### Current State

The release workflow (`.github/workflows/release.yml`) builds macOS DMGs on `macos-14` (aarch64) and `macos-13` (x86_64) runners. It signs with Apple Developer certificate and notarises.

### What's Needed for iOS

| Requirement | Detail |
|-------------|--------|
| **Runner** | `macos-14` (already used). Xcode is pre-installed on GitHub macOS runners |
| **Build command** | `cargo tauri ios build` instead of `cargo tauri build` |
| **Output** | `.ipa` file instead of `.dmg` |
| **Signing** | iOS requires a separate provisioning profile + distribution certificate. Secrets needed: `IOS_CERTIFICATE`, `IOS_CERTIFICATE_PASSWORD`, `IOS_PROVISIONING_PROFILE`, `IOS_TEAM_ID` |
| **Distribution** | Upload to TestFlight via `xcrun altool --upload-app` or App Store Connect API |
| **Apple Developer Program** | Same $99/year account works for both macOS and iOS signing |

### What's Needed for Android

| Requirement | Detail |
|-------------|--------|
| **Runner** | `ubuntu-latest` (Android builds work on Linux). Needs JDK 17+, Android SDK, NDK |
| **Build command** | `cargo tauri android build` |
| **Output** | `.apk` or `.aab` (Android App Bundle) |
| **Signing** | Android keystore (JKS or PKCS12). Secrets needed: `ANDROID_KEYSTORE` (base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` |
| **NDK targets** | `aarch64-linux-android`, `armv7-linux-androideabi`, `x86_64-linux-android` (3 targets vs macOS's 2) |
| **Distribution** | Upload to Play Store via `fastlane supply` or manual upload |
| **Rust cross-compilation** | Need Android NDK toolchains installed. `cargo tauri android init` handles this, but CI needs explicit setup |

### CI Effort Estimate

- iOS CI job: 1-2 days (reuse existing macOS runner, add iOS signing steps)
- Android CI job: 2-3 days (new runner setup, Android SDK/NDK installation, cross-compilation, signing)
- TestFlight upload automation: 0.5-1 day
- Play Store upload automation: 0.5-1 day

## 7. Recommended First Steps

### Step 1: Proof of concept — single webview on iOS simulator (2-4 hours)

```bash
cd /path/to/SGraph-AI__Desktop
npx tauri ios init
npx tauri ios dev
```

**Goal:** Verify that the app launches and `send.sgraph.ai` loads in a webview on iOS simulator. This validates the most critical assumption (remote webview loading works on mobile Tauri).

**What to watch for:**
- Does `WebviewUrl::External(url)` load correctly?
- Does `window.add_child()` work or crash?
- Is the remote site usable (touch events, scrolling, forms)?

### Step 2: Validate multi-webview on mobile (4-8 hours)

If Step 1 works, test switching between all four sites. Check:
- Memory usage with 4 webviews loaded
- Show/hide behaviour
- Layout positioning (the hardcoded `SIDEBAR_WIDTH` offset)

### Step 3: Platform-conditional layout constants (2-4 hours)

Make `SIDEBAR_WIDTH` and `STATUS_BAR_HEIGHT` configurable or platform-conditional:

```rust
#[cfg(mobile)]
const SIDEBAR_WIDTH: f64 = 0.0;
#[cfg(not(mobile))]
const SIDEBAR_WIDTH: f64 = 60.0;
```

### Step 4: Gate desktop-only APIs (1 hour)

Add `#[cfg(not(mobile))]` to `toggle_devtools` or make it return `Ok(())` on mobile.

### Step 5: Android proof of concept (4-8 hours)

```bash
npx tauri android init
npx tauri android dev
```

Same validation as iOS. Android WebView has different quirks (keyboard handling, back button, system bars).

### Summary: Minimum viable mobile proof-of-concept = 2-3 days

This gets you: "SG/Send loads and is usable in iOS simulator and Android emulator." The UI will look like the desktop layout on a phone screen (functional but awkward). This is enough to validate the approach before investing in responsive UI or mobile features.

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Multi-webview `add_child` doesn't work on mobile | Medium | High — requires architecture change | Test in Step 1. Fallback: single webview with URL navigation instead of multiple hidden webviews |
| Apple App Store rejects as "web wrapper" (guideline 4.2) | Medium-High | Medium — delays distribution | Add native features (biometric, Keychain, offline) before submission. Start with TestFlight (no review for beta) |
| Remote site (`send.sgraph.ai`) not touch-optimised | High | Medium — app works but UX is poor | This is a SG/Send concern, not a Desktop concern. The remote site needs responsive CSS independently |
| Android WebView rendering differences | Medium | Low — cosmetic issues | Test on multiple Android versions (API 24+). WebView is more fragmented than WKWebView |
| Share sheet requires native platform code | Certain | Medium — most complex mobile feature | Defer to Phase 3. Use `tauri-plugin-dialog` file picker as interim |

## Conclusion

The codebase is in good shape for mobile exploration. The Tauri 2.0 setup (`mobile_entry_point`, correct `crate-type`, minimal dependencies) means the scaffolding step will work without code changes. The main unknowns are:

1. **Multi-webview child positioning on mobile** — must be validated empirically
2. **App Store acceptance** — web wrapper risk is real
3. **Remote site responsiveness** — outside this repo's control

Recommended approach: spend 2-3 days on a proof-of-concept (Steps 1-5 above) before committing to responsive UI or mobile features. If multi-webview works on mobile, the path is clear. If it doesn't, we need an architecture discussion about switching to single-webview navigation.

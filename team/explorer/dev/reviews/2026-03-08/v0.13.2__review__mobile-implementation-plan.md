- Wants to understand feasibility on both platforms early

| Phase | Scope | Estimate | Deliverable |
|-------|-------|----------|-------------|
| **0: Restructure** | Move `src/` to `src/{core,desktop,ios,android}/` layout, update imports and `tauri.conf.json` | 2-3 hours | Clean multi-platform folder structure, desktop still works |
| **1: Scaffold both platforms** | Run `tauri ios init` + `tauri android init`, resolve compile errors, get both launching on simulators | 1-2 days | App opens on iOS Simulator + Android Emulator, shows welcome screen |

## Phase 1: Scaffold Both Platforms (Detail)

### iOS

```bash
cargo tauri ios init
```

This creates:
- `src-tauri/gen/apple/` — Xcode project
- `src-tauri/gen/apple/SGraph Desktop.xcodeproj`
- App icons need generating: `cargo tauri icon src-tauri/icons/icon.png`

**Prerequisites:** Xcode 15+ installed (for local dev). CI already has macOS runners.

### Android

```bash
cargo tauri android init
```

This creates:
- `src-tauri/gen/android/` — Gradle project
- `src-tauri/gen/android/app/src/main/`

**Prerequisites:** Android Studio, JDK 17+, Android SDK (API 26+), Android NDK.

### Expected Issues

1. **Icon sizes** — Mobile requires more icon variants than desktop. Use `cargo tauri icon` to generate all sizes from the existing 128x128 source.
2. **Bundle identifier** — Need to set: `ai.sgraph.desktop` (or similar) for both iOS and Android.
3. **Minimum API levels** — iOS 15+, Android API 26+ (Android 8.0).

## Phase 3-4: Mobile Shells (Detail)

### iOS Shell (v0/v0.1/v0.1.0)

```javascript
// src/ios/v0/v0.1/v0.1.0/app-shell-ios.js
class AppShellIos extends HTMLElement {
    connectedCallback() {
        this.innerHTML = `
            <div class="ios-content">
                <div class="webview-container" id="content-area"></div>
            </div>
            <sg-tab-bar></sg-tab-bar>
        `;
    }
}
customElements.define('sg-app-shell-ios', AppShellIos);
```

Key iOS considerations:
- **Safe areas** — `env(safe-area-inset-top)`, `env(safe-area-inset-bottom)` for notch/home indicator
- **iPad split view** — larger screen supports side-by-side; tab bar can be wider
- **Status bar** — iOS status bar overlays the app; need padding at top

### Android Shell (v0/v0.1/v0.1.0)

```javascript
// src/android/v0/v0.1/v0.1.0/app-shell-android.js
class AppShellAndroid extends HTMLElement {
    connectedCallback() {
        this.innerHTML = `
            <div class="android-content">
                <div class="webview-container" id="content-area"></div>
            </div>
            <sg-bottom-nav></sg-bottom-nav>
        `;
    }
}
customElements.define('sg-app-shell-android', AppShellAndroid);
```

Key Android considerations:
- **System navigation bar** — Android's 3-button nav or gesture nav affects bottom spacing
- **Back button** — Android hardware/gesture back must go to previous site, not exit app
- **Status bar colour** — should match app theme

## Signing & Distribution

### iOS (Reuses Existing Apple Developer Account)

| Item | Status | Detail |
|------|--------|--------|
| Apple Developer account | **Already have** | Same $99/year account used for macOS signing |
| iOS distribution certificate | **Needs creating** | Generate in Apple Developer portal → Certificates |
| Provisioning profile | **Needs creating** | App Store distribution profile for `ai.sgraph.desktop` |
| App Store Connect | **Needs setup** | Create app listing, screenshots, metadata |
| TestFlight | **Available** | Part of App Store Connect — free beta distribution |

**Dinis's existing Apple ID works for iOS/iPad signing.** The Apple Developer Program membership covers macOS, iOS, iPadOS, watchOS, tvOS, and visionOS.

### Android (Needs New Google Play Developer Account)

| Item | Status | Detail |
|------|--------|--------|
| Google Play Developer account | **Needs creating** | One-time $25 fee (vs Apple's $99/year) |
| Android keystore | **Needs creating** | JKS or PKCS12 keystore for app signing |
| Google Play Console | **Needs setup** | App listing, screenshots, privacy policy |
| APK signing | **Needs CI secrets** | `ANDROID_KEYSTORE` (base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` |
| Internal testing track | **Available** | Google Play Console allows internal testing (up to 100 testers) without full review |

**Android signing is completely separate from Apple.** Google Play uses its own keystore format. The Google Play Developer account is a different account from Apple.

### CI Secrets Needed (New)

```
# iOS (additional to existing Apple secrets)
IOS_CERTIFICATE            # iOS distribution certificate (p12, base64)
IOS_CERTIFICATE_PASSWORD   # Certificate password
IOS_PROVISIONING_PROFILE   # Provisioning profile (base64)

# Android (all new)
ANDROID_KEYSTORE           # Keystore file (base64)
ANDROID_KEYSTORE_PASSWORD  # Keystore password
ANDROID_KEY_ALIAS          # Key alias within keystore
ANDROID_KEY_PASSWORD       # Key password
```

## App Store Strategy

### Apple App Store (iOS/iPad)

**Risk: Guideline 4.2 rejection ("web wrapper").**

Mitigation plan:
1. Phase 1-4 — get the app working with basic native shell (bottom tabs, safe areas)
2. Before submission — add at least 2 native features:
   - Biometric authentication (Face ID / Touch ID) via `tauri-plugin-biometric`
   - Native share sheet or file handling
3. Submit to TestFlight first (no review required for beta)
4. Submit to App Store with clear description of native features
5. If rejected, add more native functionality and re-submit

### Google Play Store (Android)

**Lower risk** — Google is less strict about web wrapper apps. Google Play's policies focus more on content than implementation.

Mitigation:
1. Start with internal testing track (up to 100 testers, no review)
2. Graduate to open testing, then production
3. Ensure privacy policy and data safety disclosures are complete

## What Dinis Should Expect from Phase 1-2

Setting expectations clearly:

| What will work | What won't work well |
|---------------|---------------------|
| App launches on both platforms | SG/Send UI will be cramped on Android phone |
| Sites load in webviews | No touch optimisation on the remote sites |
| Bottom tab navigation switches sites | No biometric auth, share sheet, or push notifications |
| iPad shows sites at near-desktop quality | Android may have WebView rendering quirks |
| Basic native chrome (status bar, tabs) | Welcome screen layout not optimised for mobile |

**This is the "how hard is it?" exploration.** The answer from the previous review: the scaffolding is straightforward, the UX refinement is the long tail.

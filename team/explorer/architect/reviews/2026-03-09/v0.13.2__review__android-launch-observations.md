# Architect Review: Android Launch Observations

**Date:** 2026-03-09
**Version:** v0.13.2
**Reviewed by:** Architect (Explorer team)

---

## Architectural Validation

The first Android launch confirms several architecture decisions from the v0.13.2 mobile plan:

### Confirmed Working

1. **Remote webviews on Android** — Chromium-based system WebView successfully loads `vault.sgraph.ai` and `tools.sgraph.ai`. The core architectural bet (remote webviews, not bundled apps) holds on mobile.

2. **Bottom tab navigation** — The mobile app shell with bottom tabs (Send, Vault, Workspace, Tools) renders correctly. This validates the platform-specific shell approach (sidebar on desktop, bottom tabs on mobile).

3. **Site branding in header** — Each tab shows its site identity ("SG/Vault", "SG/Tools") in the header bar, confirming the mobile shell properly tracks active site state.

4. **Minimal Rust surface pays off** — Only 3 Rust commands exist, which meant minimal platform-gating needed for mobile compilation.

### Issue Discovered: Server-Side Response Headers

**`send.sgraph.ai`** returns `net::ERR_BLOCKED_BY_RESPONSE`, while Vault and Tools load fine. This reveals an inconsistency across the SGraph ecosystem:

| Site | Loads in Android WebView | Likely Header |
|------|-------------------------|---------------|
| `vault.sgraph.ai` | Yes | No restrictive frame policy |
| `tools.sgraph.ai` | Yes | No restrictive frame policy |
| `send.sgraph.ai` | **No** | `X-Frame-Options: DENY` or `frame-ancestors 'none'` |
| `workspace.sgraph.ai` | Untested | Unknown |

**Recommendation:** All `*.sgraph.ai` sites should have consistent response header policies. Options:
- Remove `X-Frame-Options` from `send.sgraph.ai` (if only used for anti-clickjacking — WebView is not an iframe attack vector)
- Set `Content-Security-Policy: frame-ancestors 'self' https://*.sgraph.ai` across all sites
- Or add a Tauri-specific origin allowance if fine-grained control is needed

This is a **server-side fix** outside this repository's scope.

### WebKit vs Chromium — First Real Data Point

The v0.13.2 plan flagged WebKit (iOS/macOS) vs Chromium (Android) as a MEDIUM risk. Now we have evidence:
- Chromium WebView renders the SGraph sites well (Tools page cards, Vault form inputs, styling all correct)
- No visual regressions observed vs the macOS WebKit rendering
- This lowers the cross-engine risk rating from MEDIUM to LOW for current functionality

## CI Architecture Note

The `ci-pipeline__android.yml` workflow uses a cache restore/save pattern for Tauri CLI that persists even on build failure — good resilience for iterative development. The Android build matrix targets `aarch64-linux-android` with NDK integration via Tauri's built-in mobile tooling.

## Recommendations

1. **Standardise `*.sgraph.ai` response headers** — this is the only blocker for a fully functional Android app
2. **Test `workspace.sgraph.ai`** on Android — confirm it loads or has the same header issue
3. **Proceed with iOS build** — the architecture is validated; iOS should be lower risk (same WebKit engine as macOS)
4. **Physical device testing** — emulator results are promising but real devices may reveal touch/scroll/performance differences

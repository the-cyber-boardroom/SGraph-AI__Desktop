## Revised Architecture: IFD Multi-Platform Model

### The Key Insight: Platform Root + Shared Core

Following IFD principles, each platform gets its own **root** — the entry point that starts the IFD version chain. Below the root, a shared **core** layer provides platform-agnostic functionality.

```
src/
  core/                          # Shared across ALL platforms
    lib/
      event-bus.js               # EventBus (already exists at src/lib/)
      site-manager.js            # SiteManager (already exists at src/lib/)
      site-config.js             # Site definitions (Send, Vault, Workspace, Tools)
    assets/
      styles/
        tokens.css               # CSS custom properties (colors, fonts, spacing)
        reset.css                # CSS reset

  desktop/                       # macOS Desktop root (IFD starts here)
    v0.1.0/
      app-shell.js               # Desktop grid layout: sidebar + content
      app-shell.css
      sidebar.js                 # Vertical icon sidebar (60px left)
      sidebar.css
      status-bar.js              # Footer URL bar
      status-bar.css
    index.html                   # Desktop entry point

  ios/                           # iOS/iPad root (IFD starts here)
    v0.1.0/
      app-shell-ios.js           # iOS layout: content + bottom tabs
      app-shell-ios.css          # Safe areas, large touch targets
      tab-bar.js                 # Bottom tab navigation
      tab-bar.css
    index.html                   # iOS entry point

  android/                       # Android root (IFD starts here)
    v0.1.0/
      app-shell-android.js       # Android layout: content + bottom nav
      app-shell-android.css      # Material-style nav, system bars
      bottom-nav.js              # Android bottom navigation
      bottom-nav.css
    index.html                   # Android entry point
```

### Why This Follows IFD

1. **Each platform root is independent** — `desktop/v0.1.0/` can evolve to `desktop/v0.1.1/` without affecting `ios/v0.1.0/`.
2. **Surgical overrides work per-platform** — `ios/v0.1.1/tab-bar.js` can override a single method from `ios/v0.1.0/tab-bar.js`.
3. **Major versions consolidate per-platform** — `ios/v0.2.0/` merges all `ios/v0.1.x/` patches into complete files.
4. **Shared core is version-stable** — `core/lib/event-bus.js` is imported by all platforms. Changes to core are rare and affect all platforms equally (by design).

### Platform-Specific Entry Points

Each platform's `index.html` loads core first, then its own components:

```html
<!-- ios/index.html -->
<head>
    <link rel="stylesheet" href="../core/assets/styles/reset.css">
    <link rel="stylesheet" href="../core/assets/styles/tokens.css">
    <link rel="stylesheet" href="v0.1.0/app-shell-ios.css">
    <link rel="stylesheet" href="v0.1.0/tab-bar.css">
</head>
<body>
    <sg-app-shell-ios></sg-app-shell-ios>
    <script type="module" src="../core/lib/event-bus.js"></script>
    <script type="module" src="../core/lib/site-manager.js"></script>
    <script type="module" src="v0.1.0/tab-bar.js"></script>
    <script type="module" src="v0.1.0/app-shell-ios.js"></script>
</body>
```

### Tauri Configuration

`tauri.conf.json` needs platform-aware `frontendDist`:

```json
{
  "build": {
    "frontendDist": "../src/desktop"
  }
}
```

For mobile builds, Tauri's `tauri.ios.conf.json` and `tauri.android.conf.json` override this:

```json
// tauri.ios.conf.json
{
  "build": {
    "frontendDist": "../src/ios"
  }
}
```

```json
// tauri.android.conf.json
{
  "build": {
    "frontendDist": "../src/android"
  }
}
```

This cleanly routes each platform to its own root.

## Rust Architecture: Platform-Gated Commands

### Current Commands (Desktop)

| Command | Mobile status |
|---------|--------------|
| `get_sites()` | Works as-is on all platforms |
| `activate_site()` | Needs `#[cfg(mobile)]` / `#[cfg(not(mobile))]` variants |
| `toggle_devtools()` | Desktop-only — gate with `#[cfg(not(mobile))]` |

### Mobile Webview Strategy

On mobile, use **single-webview navigation** rather than multi-webview `add_child()`:

```rust
#[tauri::command]
pub fn activate_site(window: Window, site_id: String, url: String) -> Result<(), String> {
    #[cfg(not(mobile))]
    {
        // Desktop: multi-webview child pattern (existing code)
        // Creates/shows native webview per site
    }

    #[cfg(mobile)]
    {
        // Mobile: navigate the single content webview to the URL
        // Or use Tauri's webview navigation API
    }
}
```

### Platform-Specific Layout Constants

```rust
#[cfg(mobile)]
const SIDEBAR_WIDTH: f64 = 0.0;
#[cfg(not(mobile))]
const SIDEBAR_WIDTH: f64 = 60.0;

#[cfg(mobile)]
const STATUS_BAR_HEIGHT: f64 = 0.0;
#[cfg(not(mobile))]

```

## Screen Size Considerations

Dinis correctly notes that the `*.sgraph.ai` sites won't be usable on small screens yet. This is **expected and acceptable** for Phase 1.

| Device | Screen | Expected UX |
|--------|--------|-------------|
| **Android phone** | ~6" (360-412pt width) | Sites will overflow, require horizontal scrolling. Navigation via bottom tabs works. |
| **iOS iPad** | 10.9-12.9" | Sites will render closer to desktop experience. Most SG tools should be usable. |
| **Android tablet** | 10-11" | Similar to iPad — reasonable experience for *.sgraph.ai sites. |

**iPad is the sweet spot** for initial testing — large enough screen that the web apps render well, and iOS/WebKit gives us the closest match to the macOS desktop app.

**Android phone is the stress test** — tells us how badly things break at small viewport widths, which informs the SG/Send team about responsive design priorities.

## Migration Path from Current Structure

### Current
```
src/
  app-shell/v0.1.0/app-shell.{js,css}   → moves to src/desktop/v0.1.0/
  sidebar/v0.1.0/sidebar.{js,css}        → moves to src/desktop/v0.1.0/
  status-bar/v0.1.0/status-bar.{js,css}  → moves to src/desktop/v0.1.0/
  lib/event-bus.js                        → moves to src/core/lib/
  lib/site-manager.js                     → moves to src/core/lib/
  assets/styles/theme.css                 → splits: tokens to core, layout to desktop
  assets/styles/reset.css                 → moves to src/core/assets/styles/
  index.html                              → moves to src/desktop/index.html
```

### Decision Required

This restructuring is a **breaking change** to the current folder layout. Two options:

**Option A: Restructure now** — Move files to the new platform-aware layout before starting mobile work. Clean break, clear structure. Risk: touches many paths, all imports need updating.

**Option B: Add mobile alongside** — Keep existing `src/` structure for desktop, add `src/ios/` and `src/android/` that import from the existing paths. Less disruption. Risk: inconsistent structure (desktop at `src/app-shell/`, mobile at `src/ios/`).

**Recommendation: Option A.** The codebase is small (6 JS files, 4 CSS files, 1 HTML). Restructuring now is a 1-hour task and sets the right foundation.

## Summary

| Decision | Recommendation |
|----------|---------------|
| **Platform architecture** | IFD with unique root per platform + shared core |
| **Build both iOS + Android** | Yes — start with both, use iPad + Android phone for testing |
| **Shell strategy** | Completely separate shell per platform (not responsive desktop shell) |
| **Webview model (mobile)** | Single-webview navigation (not multi-webview) |
| **Folder structure** | Restructure to `src/{core,desktop,ios,android}/` |
| **UX expectations** | Accept limited usability on phones; iPad will be the better initial experience |
| **App Store path** | iOS reuses Apple Developer account; Android needs Google Play keystore |

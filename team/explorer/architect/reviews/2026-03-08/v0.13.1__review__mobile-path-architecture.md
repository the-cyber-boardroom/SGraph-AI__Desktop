## 1. Architecture Assessment: Is Extending to Mobile Sound?

**Verdict: Architecturally sound, but requires targeted changes.**

The current codebase is well-positioned for mobile extension. Several decisions already made work in our favour:

- **`lib.rs` already has `#[cfg_attr(mobile, tauri::mobile_entry_point)]`** — the Rust entry point is mobile-aware from day one. The `main.rs` desktop entry simply calls `sgraph_desktop_lib::run()`, and on mobile the library crate (compiled as `cdylib`/`staticlib` per `Cargo.toml`) serves as the native entry point directly.

- **Remote webviews as the core pattern** — the app loads `*.sgraph.ai` URLs in native webviews rather than bundling web app code. This means the mobile app inherits the same approach: the SG/Send frontend team controls the web UI, and the shell just provides native framing.

- **Minimal Rust surface** — only 3 commands exist (`get_sites`, `activate_site`, `toggle_devtools`). The less platform-specific Rust code we have, the less we need to adapt.

**Architectural changes required:**

| Area | What needs to change | Why |
|------|---------------------|-----|
| **Webview layout** | `webviews.rs` hardcodes `SIDEBAR_WIDTH = 60.0` and positions webviews relative to a left sidebar | Mobile needs different layout geometry (no sidebar, or bottom tabs) |
| **Window model** | `activate_site()` uses `window.add_child()` with absolute positioning | On mobile, Tauri uses a single-webview model — child webviews are not available in the same way |
| **DevTools** | `toggle_devtools` command — irrelevant on mobile | Should be `#[cfg(not(mobile))]` gated |
| **CSP** | `frame-src https://*.sgraph.ai` in `tauri.conf.json` | May need adjustment for mobile deep links and share sheet URLs |

## 2. Tauri v2 Mobile Reality Check

The brief positions mobile support as mature and straightforward. This is partially true but needs qualification.

### What works well

- **`tauri ios init` / `tauri android init`** scaffolds real Xcode/Gradle projects. The tooling is stable in Tauri 2.x.
- **Single Rust codebase** compiles to both platforms. The `crate-type = ["lib", "cdylib", "staticlib"]` in our `Cargo.toml` already covers iOS (staticlib) and Android (cdylib).
- **Tauri plugins** generally work cross-platform. The `tauri-plugin-opener` we use is mobile-compatible.

### Gotchas and limitations

1. **Multi-webview on mobile is limited.** The desktop app's core architectural pattern is multi-webview: one "main" webview for the app shell, plus one native webview per site created via `window.add_child()`. On iOS and Android, Tauri's multi-webview support is experimental. **This is the single biggest architectural blocker.** On mobile, the more reliable approach is a single webview that navigates between URLs, or uses iframes (which our CSP already allows via `frame-src`).

2. **Remote webview navigation control.** On desktop, each site gets an isolated native webview, so navigation within `send.sgraph.ai` stays contained. On mobile with a single-webview model, we need to handle navigation interception differently to prevent users from navigating away from `*.sgraph.ai` domains.

3. **Hot-module replacement** works on mobile dev, but remote webviews that load external URLs do not benefit from HMR — we are loading live production sites, not local dev assets.

4. **`toggle_devtools`** is not available on mobile WebViews. Safari Web Inspector (iOS) and Chrome DevTools (Android) are used instead, outside the app.

5. **The `unstable` feature flag** in our Tauri dependency is concerning for mobile. We should verify which unstable APIs we depend on and whether they are available on mobile targets.

## 3. IPC and Security

### Current IPC model

The capability system in `capabilities/default.json` is minimal:
```json
{
  "permissions": ["core:default", "opener:default"]
}
```

This scopes permissions to the `main` window only. Site webviews (labelled `site-send`, `site-vault`, etc.) receive no IPC permissions — they cannot call Rust commands. This is good security design: remote sites cannot invoke native code.

### Mobile translation

- **The capability model works the same on mobile.** Tauri v2 capabilities are platform-agnostic.
- **Mobile-specific concern: deep links.** If we implement share sheet integration, the app must handle incoming `sgraph://` or universal link URLs. These need new Tauri commands and corresponding capability grants, which should be scoped carefully to avoid granting remote webview content access to native APIs.
- **Biometric auth** (Face ID, fingerprint) requires `tauri-plugin-biometric`. This introduces a new permission surface. The biometric prompt must be triggered only from trusted local UI, never from remote webview content.
- **Keychain on mobile.** iOS Keychain and Android Keystore are the equivalents of macOS Keychain. The `security-framework` crate (listed in the reality doc as planned) works on iOS but not Android. Android would need a separate implementation via JNI or a Tauri plugin.

### Security recommendations for mobile

1. Remote webview content must never gain `invoke()` access — maintain the current isolation.
2. All native feature triggers (biometric, camera, share) must originate from the local app shell, not from remote webview JavaScript.
3. Consider a message-passing bridge (postMessage) between remote webviews and the app shell for controlled communication, rather than granting IPC capabilities to remote webviews.

## 4. WebView Differences: WebKit vs Chromium

### The core issue

| Platform | WebView engine | Implications |
|----------|---------------|--------------|
| macOS | WebKit (system) | What we test on today |
| iOS | WebKit (WKWebView) | Same engine as macOS — high compatibility expected |
| Android | System WebView (Chromium-based) | Different engine — rendering, JS APIs, and behaviour can differ |

### Specific implications for our remote webview approach

1. **iOS is the easy win.** Same WebKit engine, same rendering. The SG/Send web UI that works in the macOS app will work in the iOS app with no changes. This argues strongly for iOS-first.

2. **Android introduces cross-browser concerns.** The SG/Send frontend must already work in Chrome (since users access it via browser), so Chromium-based WebView compatibility is likely fine. But subtle differences exist:
   - CSS `-webkit-` prefixed properties may behave differently
   - JavaScript API availability (e.g., `crypto.subtle`, `File` API) varies by Android WebView version
   - Android WebView update cycle is independent of the OS — older devices may have outdated WebViews

3. **Drag-and-drop.** Our desktop app specifically disables Tauri's drag-drop handler (`.disable_drag_drop_handler()`) so WebKit handles native drops. On mobile, drag-and-drop does not exist as a user interaction. The file input must change to a file picker or camera capture.

4. **CSP enforcement.** WebKit and Chromium handle CSP slightly differently. Our current CSP (`default-src 'self'; script-src 'self' 'unsafe-inline'`) applies to the main window. On mobile, if we shift to a single-webview model, the CSP for the app shell and the CSP for remote content need to be reconciled.

## 5. Recommended Architecture for Mobile

### Do NOT use the same app-shell on mobile

The current `sg-app-shell` component renders a CSS Grid layout with `grid-template-columns: var(--sidebar-width) 1fr`. The sidebar is a vertical icon bar occupying 60px on the left. This layout is fundamentally desktop-oriented.

**Recommended approach: platform-aware app shell selection.**

```
src/
  app-shell/
    v0.1.0/
      app-shell.js         # Desktop (existing)
      app-shell.css        # Desktop (existing)
    mobile/
      app-shell-mobile.js  # Mobile variant
      app-shell-mobile.css # Bottom tabs, full-width content
```

The entry point (`index.html`) should detect the platform and load the appropriate shell:

```javascript
const isMobile = window.__TAURI__?.internals?.isMobile ?? false
if (isMobile) {
    import('/app-shell/mobile/app-shell-mobile.js')
} else {
    import('/app-shell/v0.1.0/app-shell.js')
}
```

### Mobile app shell architecture

| Element | Mobile design |
|---------|--------------|
| Navigation | Bottom tab bar (4 icons: Send, Vault, Workspace, Tools) |
| Content area | Full-width, full-height single webview |
| Status bar | Remove or collapse into native status bar |
| Welcome screen | Simplified — single column, larger touch targets |
| Settings | Full-screen slide-over, not a sidebar icon |

### Single webview on mobile

Instead of creating child webviews per site (the desktop pattern), the mobile shell should:

1. Use a **single content webview** that navigates to the selected site URL.
2. Cache-friendly: when switching sites, store the scroll position and state, then navigate the webview to the new URL.
3. Alternatively, if multi-webview stabilises in Tauri mobile, the child webview pattern can be adopted later.

This means `activate_site` in Rust needs a mobile-specific code path:

```rust
#[cfg(mobile)]
// Navigate existing webview to new URL
#[cfg(not(mobile))]
// Current child webview pattern
```

### Shared code

These components and libraries should remain shared across desktop and mobile:

- `EventBus` (`src/lib/event-bus.js`)
- `SiteManager` (`src/lib/site-manager.js`) — with platform-aware activation logic
- Site configuration (`sites.rs` / `sgraph-sites.json`)
- Theme tokens (`theme.css`) — augmented with mobile-specific overrides

## 6. Risk Assessment

### HIGH RISK

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Multi-webview not supported on mobile** | Core desktop architecture breaks. Cannot create per-site child webviews. | Design mobile path around single-webview navigation from the start. Do not assume desktop architecture transfers. |
| **Apple App Store review rejection** | Remote-only apps (WKWebView loading external URLs with no local content) may be rejected under App Store guideline 4.2 (Minimum Functionality). | Ensure the app provides native value beyond a web wrapper: biometric auth, offline queue, share sheet, push notifications. Provide meaningful local UI in the app shell. |
| **Android WebView fragmentation** | Older devices with outdated system WebView may break the SG/Send frontend. | Set minimum Android API level to 26+ (Android 8.0) and minimum WebView version. Test on real devices with different WebView versions. |

### MEDIUM RISK

| Risk | Impact | Mitigation |
|------|--------|------------|
| **CSP incompatibility** | Mobile webview CSP enforcement differs from desktop; may break remote site loading. | Test CSP configuration on iOS simulator and Android emulator early (Phase 1). |
| **Plugin availability** | Some Tauri plugins (biometric, camera, push) may have incomplete mobile implementations. | Audit plugin maturity before committing to feature set. Build features behind capability flags. |
| **Build pipeline complexity** | Adding iOS and Android builds to CI/CD doubles the matrix. macOS runner needed for iOS builds. | Use separate workflow files for mobile builds. iOS builds require macOS runners (available on GitHub Actions). Android builds can use Linux runners. |
| **Code signing for three platforms** | Apple codesigning (macOS + iOS), Google Play signing (Android) — three different signing processes in CI. | Phase signing setup: macOS is done, iOS next (same Apple Developer account), Android last. |

### LOW RISK

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Rust code changes** | Minimal Rust code exists; most is webview management. | Platform-gated code (`#[cfg(mobile)]`) keeps changes isolated. |
| **Theme/styling** | CSS custom properties already abstract theming. | Add mobile-specific overrides without changing desktop styles. |

## 7. Phasing Assessment

The brief proposes:

1. Basic mobile build (1-2 days)
2. Responsive UI (3-5 days)
3. Mobile-specific features (1-2 weeks)
4. App Store submission (2-3 days)

### Architect's assessment of each phase

**Phase 1: Basic mobile build — AGREE with caveat**

`tauri ios init` and `tauri android init` will scaffold projects. Getting the app to compile and launch on simulators is realistic in 1-2 days. However, the brief underestimates the multi-webview issue. The app will likely crash or show a blank content area because `window.add_child()` may not work on mobile. Expect to spend additional time adapting the webview management to work on mobile.

**Recommendation:** Phase 1 should include a spike to validate whether `add_child()` works on iOS/Android simulators. If not, the single-webview approach must be implemented before anything else is usable.

**Phase 2: Responsive UI — AGREE, but reframe as "mobile app shell"**

This is not just CSS responsive design. It requires a new app shell component with bottom tab navigation, a different webview management strategy, and touch-optimised interactions. 3-5 days is realistic if the multi-webview question is resolved in Phase 1.

**Phase 3: Mobile-specific features — AGREE on scope, cautious on timeline**

Each feature (share sheet, biometrics, camera, push) is its own mini-project with platform-specific native code. 1-2 weeks is achievable if we pick 2-3 features, not all 5.

**Recommended priority order:**
1. Share sheet integration (highest user value on mobile)
2. Biometric auth (security differentiator)
3. Camera upload (natural mobile interaction)
4. Push notifications (requires backend infrastructure — may belong in a later phase)
5. Offline queue (complex state management — defer)

**Phase 4: App Store submission — AGREE, with App Store risk noted**

The 2-3 day estimate for submission mechanics is reasonable. However, Apple review is unpredictable. The biggest risk is rejection under guideline 4.2 (see Risk Assessment above). We should have at least 2 native-exclusive features (biometric + share sheet) before submitting.

### Recommended revised phasing

| Phase | Scope | Estimate |
|-------|-------|----------|
| **0: Spike** | Run `tauri ios init`, validate webview behaviour on iOS simulator, confirm or refute multi-webview support | 1 day |
| **1: iOS shell** | Mobile app shell with bottom tabs, single-webview navigation, iOS-specific layout | 3-4 days |
| **2: Android port** | Adapt to Android WebView, test on emulator, resolve Chromium-specific issues | 2-3 days |
| **3: Native features** | Share sheet + biometric auth (minimum for App Store viability) | 1 week |
| **4: Distribution** | TestFlight (iOS), APK (Android), CI/CD pipeline extension | 2-3 days |
| **5: App Store** | Screenshots, metadata, submission, review cycle | 3-5 days (including buffer for rejection) |

### Why iOS first

- Same WebKit engine as our macOS app — lowest risk for remote webview compatibility.
- Same Apple Developer account already set up for code signing.
- TestFlight distribution is simpler for beta testing than APK sideloading.
- If App Store review reveals issues, we learn before investing in Android.

---

## 8. Summary of Recommendations

1. **Validate multi-webview on mobile before committing to any timeline.** This is the gating question.
2. **Build a separate mobile app shell** rather than making the desktop shell responsive. The navigation model is fundamentally different.
3. **Target iOS first.** Same WebKit engine, same Apple account, lower risk.
4. **Use single-webview navigation on mobile** until Tauri's mobile multi-webview support matures.
5. **Gate Rust code by platform** (`#[cfg(mobile)]` / `#[cfg(not(mobile))]`) rather than maintaining separate codebases.
6. **Implement at least 2 native features** (share sheet + biometrics) before App Store submission to avoid 4.2 rejection.
7. **Do not attempt push notifications in the initial mobile release.** It requires backend infrastructure that does not exist.
